# S18 -- Mobile Polish + WeekView Agenda

**Repo**: main | **Type**: FE | **Phase**: V2
**Size**: M | **Dependencies**: S15, S16, S16b, S17 (mobile pass must see the final UI: cleaned Reports, time-bound entries with new EntryChip prefix, inline edit modal)
**Plan Sources**: docs/V2_FEATURE_PLAN.md (decisions #2, #7)

> **Goal:** make HourTrack pleasant to use on a phone. Two coordinated
> changes: (a) a mobile-first responsive pass across MonthView,
> EntryEditor, Reports, EntryEditModal, CalendarHeader; (b) a dedicated
> **Agenda view** for WeekView on mobile (`< md`) that replaces the
> unreadable 7-column grid with a vertical list grouped by day, mirroring
> Google Calendar's "Schedule" mode.

## Notes

- **Mobile-first means default-mobile.** When adding new Tailwind classes in this sprint, start with the unprefixed (mobile) class and only add `sm:` / `md:` overrides for larger screens. The codebase has been desktop-first to date; this is the cutover.
- **Breakpoints.** Stick to Tailwind defaults: `sm: 640px`, `md: 768px`, `lg: 1024px`, `xl: 1280px`. WeekView agenda triggers at `< md` (≤ 767px) — most phones in portrait. iPad portrait (768px) gets the grid view, which renders fine at that width.
- **Bottom-sheet is a Dialog variant** (Task 5): Radix Dialog's positioning is pure className. Adding a `variant?: 'centered' \| 'bottom-sheet'` prop on `DialogContent` is a one-file change with conditional Tailwind classes. Existing centered modals keep working unchanged (default is `'centered'`). EntryEditModal/CardModal/DayPickerModal opt in. Do NOT add a new bottom-sheet library — Radix gives focus management, escape handling, and overlay for free.
- **Lighthouse baseline FIRST, audit LAST** (Tasks 0a + 14): without a pre-sprint anchor on `main`, the "Perf ≥85" target is aspirational. Running Lighthouse on `main` before any work means the post-sprint diff number is meaningful — if perf regressed below 85, you know which sprint changes need backing out. Lighthouse runs are reproducible only at the same git SHA, so capture 0a BEFORE the first commit of this sprint.
- **matchMedia polyfill is non-negotiable** (Task 0b): jsdom (vitest's default DOM) does NOT implement `window.matchMedia`. Every test that imports `useMediaQuery` will throw at module-init time. The polyfill goes in `vitest.setup.ts` so it loads before any test file. Tests that need a truthy match override `window.matchMedia` per-test.
- **Touch target strategy** (Task 13): one global Button bump first, then surgical fixes for icon-only buttons that bypass `Button`. Global bump is 1-line; surgical fixes are <10 sites. Don't reverse the order — auditing 20+ touch points before the global bump means redoing half of them once the bump lands.
- **`useMediaQuery` is the new shared utility.** Until now the codebase relied on CSS-only responsive (Tailwind classes). Some logic needs JS-level branching (e.g. switching between two component implementations). Put `useMediaQuery` in `src/lib/hooks/` so it has a clear home.
- **Touch-target rule.** 44×44px comes from iOS HIG / Material Design baseline. The `Button` primitive's default size already meets this on desktop (`h-10 = 40px`) but is borderline. Bump it to `h-11` on `< sm` via a responsive utility class, or globally — pick whichever results in fewer per-call-site changes.
- **PWA safe-areas.** iOS Safari respects `env(safe-area-inset-*)` only when the viewport meta tag has `viewport-fit=cover`. Verify Task 23 includes that. Without it, layout looks fine but the home-bar overlaps content in standalone mode.
- **Performance budget.** Adding `useMediaQuery` subscriptions, additional responsive components, and the agenda view ought to be sub-5kb gzipped together. If bundle grows materially, profile in the PR description.
- **What this sprint does NOT do:**
  - Day swipe gestures (swipe left/right on agenda to change week) — that's a v2.1 enhancement if requested.
  - Pull-to-refresh — PWA already revalidates queries on focus; native gestures aren't needed.
  - A separate `/agenda` route — the agenda view is purely a responsive variant of WeekView. The user still toggles between Month and Week via CalendarHeader, and "Week" on mobile happens to render as agenda.
- **After this sprint, V2 is complete.** All 8 user requirements should be satisfied. Future polish (recurring events, time-zone awareness, swipe gestures, etc.) opens a new V3 plan if/when the user asks.
