# S27 -- Monthly Payment Tracking (per-client "paid / not paid" ledger)

**Repo**: main | **Type**: FE + Schema | **Phase**: V3 Feature
**Size**: L | **Dependencies**: S21 (`monthly` rateType + `monthlyEarningsForPeriod`), S16 (entry shape), S23 (query/cache patterns)
**Plan Sources**: user request 2026-07-12 — "відслідковувати чи було отримано оплату за виконану роботу за місяць … місяць липень і має бути запис Марі 250 отримано або не отримано, та кнопки якими це все відзначати."

> **Goal:** a new **Payments** page, filterable by month, that shows for every
> client-card the **expected** amount for that month (computed from the
> existing earnings model — hourly / fixed / monthly retainer / custom
> payments), how much was actually **received**, and a derived status chip
> (paid / partial / unpaid / overdue). One-tap **"Mark paid"** records a
> payment (amount prefilled with the remaining balance, date = today), with
> undo and an editable per-month payment history. Payment records are a new
> Dexie entity that rides the existing Drive-snapshot sync — **no Google
> Calendar side-effects, no server.**
>
> The _expected_ side already exists (S21 shipped `Card.monthlyTotal` +
> `monthlyEarningsForPeriod`; Reports already aggregates per card). This
> sprint adds only the **received** side: a `Payment` entity + the page.

## User requirements (user request 2026-07-12)

- **UR-27-1** — A page with month filtering that shows, per client, whether the money recorded in the calendar for that month was received. Example: month = July → a row "Марі — 250 — отримано / не отримано".
- **UR-27-2** — Buttons to mark the money as received (and to correct a mistake). Cash for month X is often handed over during month X+1, so the _paid-on_ date and the _period being paid for_ are independent.
- **UR-27-3** — The expected amount must agree with what the calendar/Reports already compute for that month (retainer cards like "Марі 250/міс", hourly cards, fixed cards, custom-payment entries). No second source of truth for earnings math.

## Locked design decisions (research: FreshBooks / Wave / Clockify / Bonsai / Splitwise patterns)

1. **Store payment records, derive status.** Status is never stored: `paid` = received ≥ expected; `partial` = 0 < received < expected; `unpaid` = 0 received. `overdue` is a derived _display modifier_ (unpaid/partial AND the period is a fully past month), like Clockify derives Overdue — never manually set.
2. **Multiple payments per card+month.** Partial payments are the same flow with a smaller number (FreshBooks/Wave pattern), not a separate feature. `received = sum(payments for card+period)`.
3. **`period` is explicit (`'YYYY-MM'`), not inferred from `paidOn`.** Cash for July arrives in August; both facts are kept.
4. **Amount prefilled with the remaining balance** (Splitwise settle-up pattern); date prefilled with today. One confirm tap for the common case.
5. **Undo = delete the payment record** (Splitwise) — via toast action right after creating, and via the payment-history list at any time.
6. **Out of scope:** invoices/documents, sent/unsent states, payment methods (always cash), multi-currency (EUR app-wide), carry-over balances between months, auto-reminders (S28 adds a manual quick-create hook only).

## Acceptance Criteria

### Ledger correctness (UR-27-1, UR-27-3)

- [ ] For a month, every card with ≥1 entry that month appears with an expected amount that **matches Reports** for the same period (hourly, fixed, monthly retainer, custom-payment entries)
- [ ] A `monthly` card ("Марі", `monthlyTotal: 250`) with entries in July shows expected **250** for `2026-07`; the same card with zero July entries does not appear (unless it has a July payment)
- [ ] Received = sum of that card's payments with `period = selected month`, regardless of `paidOn`
- [ ] Status chips derive correctly: paid / partial ("120 з 250 €") / unpaid; past months that aren't fully paid render as overdue
- [ ] Rollup strip totals (Expected / Received / Outstanding) are consistent with the rows

### Mark-paid flow (UR-27-2)

- [ ] "Отримано" opens the dialog prefilled with the remaining balance and today's date; one confirm creates the payment and flips the chip without a full refetch
- [ ] Entering a smaller amount produces a partial payment; a second payment for the remainder flips to paid
- [ ] Undo toast removes the just-created payment; the expanded history allows edit and delete of any payment later
- [ ] Payments survive reload (Dexie) and a Drive push → restore round-trip (snapshot v4); deleting a payment on one device wins over the stale copy on another (tombstone LWW)

### Quality

- [ ] No Google Calendar traffic from any payment operation
- [ ] New UI strings exist in uk/en/es; page is mobile-first and passes the axe e2e check
- [ ] `pnpm -F web typecheck`, `lint`, `test`, `e2e` green

## Notes

- **Expected math is read-only reuse.** If you find yourself writing rate logic in `features/payments/`, stop — extend/extract from `packages/shared-utils/src/earnings.ts` instead (S0a decides the shape). Divergence between Payments and Reports numbers is the worst failure mode of this feature.
- **Snapshot completeness is the hidden risk.** S0b's inventory is the Part A checklist: schema, snapshot build/validate/restore, LWW merge, tombstones, backup service. A payment that survives locally but vanishes after a Drive restore is data loss the user will hit weeks later.
- **`period` vs `paidOn` are independent by design** — an August 4 cash handover for July is `{ period: '2026-07', paidOn: '2026-08-04' }`. The month filter always filters by `period`.
- **Overdue is presentation, not data.** It's computed from (status, period, today) at render time. Don't persist it, don't add a cron for it.
- **What this sprint does NOT do:** reminders/notifications (S28), invoices or documents, payment methods, currencies, per-month manual adjustment of the expected amount (future — a signed adjustment record if real usage needs discounts/extras), auto-carryover of partial balances between months.
