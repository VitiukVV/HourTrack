# S28 -- Reminders (in-app + Google Calendar event)

**Repo**: main | **Type**: FE + Schema + Calendar-sync | **Phase**: V3 Feature
**Size**: M | **Dependencies**: S27 (Payments page hosts the quick-create hook), existing calendar-sync stack (S04+, `ensureCalendar`, sync queue)
**Plan Sources**: user request 2026-07-12 — "можливість додавати нагадування для себе на певну дату … 'Забрати кошти в Марі за липень' … має висвітитись при заході в додаток"; scope narrowed 2026-07-12: "нотифікація в шторці не потрібна — буде достатньо тієї яка буде в додатку і в гугл календарі."

> **Goal:** let the user create a dated reminder ("4 серпня 09:00 — Забрати
> кошти в Марі за липень") that (a) surfaces **in-app** — a due-reminders
> banner on open, plus a toast if the app happens to be open at the due
> moment — and (b) exists as a **Google Calendar event** at that date/time
> through the app's existing Calendar integration, so the user sees it in
> their calendar (and gets whatever notification the Google Calendar app
> provides, as a free side-effect — not a requirement of this sprint).
>
> **Scope decision (user, 2026-07-12):** no phone-shade delivery requirement.
> That removes the Notification API, permission prompts, and any service
> worker work entirely. No Web Push, no push backend — the delivery surfaces
> are the in-app banner/toast and the Calendar event, full stop.

## User requirements (user request 2026-07-12, narrowed same day)

- **UR-28-1** — Create a reminder with free text, a date, and a time (e.g. 2026-08-04 09:00, "Забрати кошти в Марі за липень").
- **UR-28-2** — Due reminders are shown when opening the app, until explicitly done/dismissed.
- **UR-28-3** — The reminder also appears as an event in Google Calendar at the set date/time (via the existing sync). In-app + Calendar is the complete delivery story; native shade notifications are explicitly NOT required.
- **UR-28-4** — From the Payments page (S27), quick-create a prefilled collection reminder for an unpaid month ("Забрати кошти в {card} за {місяць}").

## Notes

- **Scope was deliberately narrowed (2026-07-12).** The original ask included a phone-shade notification at the due time with the app closed. Since there is no server and no client-only scheduled-notification API (Notification Triggers is dead), that would have required push infrastructure; the user decided **in-app + Google Calendar event is sufficient**. Do not "helpfully" add Notification API, permission prompts, `injectManifest`, or any push code — that's the exact scope this revision removed.
- **The popup override on the event stays** (task 6): it's one line, and if the user's phone happens to notify from the HourTrack calendar, that's free upside. It is NOT verified, NOT an AC, and its failure is NOT a bug.
- **Done-before-due must delete the event.** The worst UX bug this feature can ship: user collects the money early, marks done, and the calendar still shows/pings the stale event on Aug 4. The delete op is queued through the same retryable sync queue, so offline done is safe.
- **`notifiedAt` prevents toast spam** from the 60s scheduler tick and from multiple tabs; it's a per-reminder stamp, not per-device — acceptable for a single-user app (documented trade-off).
- **Scope discipline:** no recurring reminders, no snooze, no reminder→payment hard link (prefill only), no Web Push / push backend, no SW changes, no reminder categories. Recurring + snooze are the likely first future asks.
- **Ordering:** S27 → S28 (task 14 touches S27's `PaymentRow`; schema bumps assume v7/v4 landed). If reversed, renumber the Dexie/snapshot versions and drop task 14 to a follow-up.
