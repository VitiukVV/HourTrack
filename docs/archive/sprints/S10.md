## Acceptance Criteria

- [ ] On first authed app open with empty Drive, `data.json` is created in appDataFolder containing local snapshot
- [ ] On second device login, Drive `data.json` is pulled and merged into local Dexie — cards/entries appear
- [ ] Editing on one device propagates to a second device after refresh (eventual consistency via Drive)
- [ ] LWW correctly resolves divergent edits per row by `updatedAt`
- [ ] Soft-deleted cards remain visible via tombstones; hard-deleted cards stay deleted on other devices
- [ ] Sync queue persists across page reloads
- [ ] Offline edits work locally; queue flushes when network returns
- [ ] ETag-based conflict detection triggers pull + merge + push, no silent overwrites
- [ ] SyncIndicator in header shows current state (synced / syncing / error)
- [ ] Token expiry mid-sync auto-refreshes via S09 logic and retries once
- [ ] All strings localized in uk/en/es
- [ ] No use of `https://www.googleapis.com/auth/drive` (full scope) — only `drive.appdata`

## Notes

- **Tombstones are essential** because absence in a snapshot is ambiguous: it could mean "deleted on device A" or "not yet synced from device B". Tombstones express intent. Keep them for 30 days then prune
- The `pushDataJson` operation is **idempotent and coalescing**: multiple enqueues within the debounce window collapse to one write. Implement at the queue layer
- **Write contention:** the SyncManager must hold an in-process lock during the rebuild-and-push cycle to prevent two concurrent pushes from racing (browser tab + visibility events)
- ETag mismatch (HTTP 412) is the normal "remote changed" signal — handle it without surfacing an error to the user
- Settings updates (theme, language) also sync via `data.json` — but they should LWW per field via the merged Settings row, not whole-object overwrite. Implement explicit per-field merge
- For Phase 2 acceptance: signing into two devices and editing on both must converge after a brief delay. Add a manual "Sync now" button in dev mode for debugging
- The `deleteCalendarEvent` op handler is registered as a no-op here; S12 replaces it with the real Calendar API call
