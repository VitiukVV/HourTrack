# S17 -- Inline Entry Edit Modal

**Repo**: main | **Type**: FE | **Phase**: V2
**Size**: S-M | **Dependencies**: S16b (modal must include the new `startMinutes` input + use the time-bound EntryEditor surface)
**Plan Sources**: docs/V2_FEATURE_PLAN.md (decision #8)

> **Goal:** let the user tap any entry on the calendar (Month / Week /
> Day views) and edit **just that one entry** in a focused modal — start
> time, duration, custom payment, note — without leaving the calendar.
> The card definitions in the header are untouched; only the clicked
> entry is modified. Save/delete go through the existing mutations so
> Google Calendar sync + Drive backups happen automatically.

## Notes

- **Why a modal, not full-page navigation:** the user explicitly said "natiska na pevnu kartku v pevnomu dni shchob vidredahuvaty same yiyi". The intent is staying in calendar context. A full-page nav (existing `/day/:date`) breaks that flow. Modal preserves it.
- **Why DayPage is excluded (Task 10):** DayPage already IS the focused per-entry editor surface — every entry has its own form rendered inline. Adding a modal on top of it would be redundant. The chip-click → modal pattern is for surfaces (MonthView, WeekView, future agenda view) where chips are read-only by default.
- **Why explicit save instead of autosave:** the autosave UX works on DayPage because the user is committed to "this is the day I'm editing." On the calendar, accidental scrolling/dragging shouldn't silently mutate an entry. Explicit Save also gives the Cancel button real meaning.
- **No `mode` enum on EntryEditor** (Task 4 — corrected from original spec): the original draft predicated the refactor on EntryEditor having an autosave indicator that needed hiding in modal mode. Reading the actual `EntryEditor.tsx`: it ALREADY uses explicit `<form onSubmit>` + Save button — there is no autosave. The cleanest contract is three additive optional props (`onSaved`, `onCancelClick`, `hideDelete`) instead of branching on a discriminator. DayPage doesn't pass them; modal does. Same form, same validation, same fields — zero duplication.
- **Why local state, not Zustand** (Task 7): the editing entry id is per-view ephemeral state — MonthView and WeekView never simultaneously have a modal open (the user is on one view at a time, the other is unmounted). A Zustand slice would be overhead for state that nothing else reads.
- **Chip overflow on MonthView:** small cells already truncate chips. After S16's time prefix lands, chip text becomes `10:00 ProjectName` — even more reason for chips to be clickable, since the user often can't read the full name and needs the modal to verify what they're editing. Confirm truncation handles long names + time prefix gracefully.
- **No new mutations needed:** all the wiring uses existing `useUpdateEntryMutation` / `useDeleteEntryMutation` from S04. The sync queue is unchanged.
- **Mobile considerations** are deferred to S18 (it'll make sure the modal renders well on small screens — full-screen on phones, centered card on tablets+).
