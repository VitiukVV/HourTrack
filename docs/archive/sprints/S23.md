# S23 -- Performance & Architecture Improvements

**Repo**: main | **Type**: FE | **Phase**: Post-V2 Polish
**Size**: L | **Dependencies**: S15 (Recharts removed), S17 (EntryEditModal), S18 (responsive layouts), S21 (monthly retainer Reports shape)
**Plan Sources**: project review chat 2026-05-23 (10 findings, prioritised by impact/effort)

> **Goal:** trim the 760 KB main bundle, eliminate avoidable re-renders on
> the calendar surface, and replace coarse `invalidateQueries(['entries',
'range'])` with surgical `setQueriesData` patches. Net effect: faster
> cold start on mobile, smoother interactions when the user edits a
> single entry on a busy month. No user-visible feature changes — every
> task is either a measurable perf win or a maintainability refactor.

## User requirements (project review chat 2026-05-23)

- **UR-23-1** — Initial JS payload on `/` (Home/Calendar) must shrink: today the home route eagerly pulls Login, Reports, Settings, DayPage, all three locale JSONs, and the entire Google + Sync layer. Cut what isn't needed before authed.
- **UR-23-2** — Editing one entry on the calendar must not invalidate every range-cache. A change on 2026-05-14 today re-runs the full month + reports queries; it should patch in place.
- **UR-23-3** — Switching months in MonthView (35–42 `DayCell` + N `EntryChip` nodes) must not re-render every cell when only the entries map identity changed; cells whose `entries` reference is unchanged should bail out.
- **UR-23-4** — Reports day-filter without any monthly-retainer card should NOT widen the entries query to the full calendar month (it currently always does).

## Notes

- **Scope discipline.** This sprint is performance + architecture only. No new user-visible features. Anything that looks like "while we're here, let me redesign X" — defer.
- **The Recharts ghost.** S13 originally lazy-loaded the Reports route specifically because Recharts was heavy. S15 removed Recharts and reverted to an eager import (per the comment in `routes.tsx:31`). Reports is still worth lazying because it transitively pulls DayPicker / MonthPicker / WeekPicker / computeReport / Virtuoso (via DayPage's `useEntriesInRange` reuse). Don't be confused by the historical comment when removing it.
- **TanStack chunk singleton trap.** The `vite.config.ts` `manualChunks` block has a load-bearing comment (lines 38-42): splitting `@tanstack/react-query` into its own chunk breaks the QueryClient singleton across lazy boundaries. The lazy-route refactor in Part A MUST NOT touch the manualChunks. If a route lazy chunk happens to dedupe TanStack into its own file via Rollup heuristics, force it back into the default chunk by importing TanStack from a shared module at the route root.
- **Surgical patch correctness boundary.** `patchEntryInRangeCaches` only patches caches whose `[start, end]` actually contains the entry's date. For a date-change update (entry moved from May 14 → May 21) the helper must remove from the old date's bucket AND insert at the new — verify with a dedicated test. The pre-mutation entry shape needs to be in scope: read it via `onMutate` (already the pattern in `useUpdateCardMutation`) and thread it through to `onSuccess`.
- **Reports cache invalidation is intentional.** `computeReport` aggregates byCard + monthly retainer math at query-time. Trying to patch its result in place would mean duplicating the aggregation logic in the patch helper. Invalidating the Reports cache subtree on each entry mutation is the correct trade — Reports is opened deliberately, not on every paint of /.
- **memo() comparator drift.** Hand-rolled comparators rot when new props are added (forget to compare → stale render). Mitigate by exporting the comparator alongside the component and adding a TS test that asserts every key of the props interface is referenced in the comparator. (Sketch: `type AllProps = keyof Props; type Used = ...derived from comparator; type Missing = Exclude<AllProps, Used>;` — `Missing` should equal `never`.) Defer if the test setup is too heavy; otherwise this is the right place to encode the invariant.
- **Bundle budget enforcement.** 500 KB is the post-S23 target. A future sprint that legitimately needs to grow it (e.g. adding charts back, or i18n with 5 languages) should raise the threshold in the same PR that ships the regression — not retroactively. The build assertion is the forcing function.
- **What this sprint does NOT do:**
  - Move `lib/google/*` + `SyncManager` behind a dynamic auth-gated import. (Considered. Adds complexity around the singleton lifecycle + bootstrap flow. Worth a dedicated S24 if cold-start on `/login` is still too slow after S23.)
  - Replace TanStack Query with a custom cache. (No.)
  - Rewrite Dexie schema. (No — see S21 schema v3.)
  - Touch the calendar visual layer (DayCell footers, EntryChip variants) — those are S21's domain.
  - Touch the sync conflict / LWW logic — well-tested, untouchable for this sprint.
