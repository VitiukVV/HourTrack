# S16b -- Time-Bound UI + Google Calendar dateTime Sync

**Repo**: main | **Type**: FE+SYNC | **Phase**: V2
**Size**: L | **Dependencies**: S16 (types, Zod schemas, Dexie v5, TimeInput primitive, pinned-TZ test setup)
**Plan Sources**: docs/V2_FEATURE_PLAN.md (decisions #1, #5)

> **Goal:** mount the time-of-day model into every UI surface and switch
> Google Calendar from all-day to time-bound events. CardForm gains a
> default-start-time input; EntryEditor adds a start-time field; entry
> creation through DayCell, DayPage, and dayClick pipes the card default
> into the new entry; EntryChip leads with the time range; ReportsTable
> sorts by `startMinutes` within a day; `buildEvent` emits
> `{ dateTime, timeZone }` payloads with strict RFC3339 discipline.

## Notes

- **Why split from S16:** S16 ships the destructive Dexie migration + types + validation in isolation. S16b consumes them. Each diff is small enough for one reviewer to hold in their head; failures stay localized to one layer.
- **RFC3339 format discipline:** Google Calendar accepts three forms in `dateTime`: with `Z` (UTC), with `±HH:MM` offset, or as a floating wall-clock string. We use the **third** form paired with the explicit `timeZone` field. Mixing forms (e.g. `Z`-suffixed dateTime + `timeZone: 'Europe/Kyiv'`) is implementation-defined and has produced `±N`-hour drift bugs in real apps. The test assertions about `!endsWith('Z')` and `!includes('+')` lock this contract in.
- **Card-default cascade rule** (Task #11/#12): changing a card's `defaultStartMinutes` does NOT retro-update existing entries' `startMinutes`. The default is a template for the next new entry, not a retroactive law. Name/color changes still cascade because they affect the visual identity of every entry-event in Google Calendar — start time doesn't.
- **Old all-day Calendar events after v1→v2:** the Dexie wipe in S16 left any pre-existing all-day Google Calendar events orphaned (we don't know to delete them — the local DB that held their eventIds was wiped). The user can manually delete them or ignore them. "Resync All" pushes fresh time-bound events for current entries but does NOT clean up orphans. Surface this honestly in `RestoreModal` copy and `SMOKE_TEST.md`.
- **Past-midnight entries** stay rejected in v2.0 via S16's `entries.validation.timeOverflow`. If users complain, fold into v2.1 by allowing `dateTime.end` to roll into the next day.
- **No new mutations.** All wiring uses existing `useUpdateEntryMutation` / `useCreateEntryMutation` / `useUpdateCardMutation`. The sync queue carries the new payload shape transparently.
