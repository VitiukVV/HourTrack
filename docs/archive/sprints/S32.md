# S32 -- Chronological Entry Ordering Across Every Day Surface

**Repo**: main | **Type**: FE + DB + Shared-utils | **Phase**: Post-V3 Polish
**Size**: S | **Dependencies**: none new (touches S06 DayPage, S04/S19 calendar surfaces, S05 day-click flow, S16 `startMinutes`, S16b Reports ordering, S23 surgical cache patch)
**Plan Sources**: user report 2026-08-15 — "swap two entries' start times and the calendar card keeps the old order; a new entry lands at the end of the day instead of at its time"

> **Goal:** make **one** ordering rule — the rule Google Calendar already applies to
> these very entries once they sync — the ordering of every surface that lists
> entries for a day:
>
> `date ASC → startMinutes ASC → durationMin DESC → createdAt ASC → id ASC`
>
> A day holds any number of entries (three and more is normal), so this is a full
> re-sort of the day, not a swap of two neighbours. Reports already orders on the
> first two tiers (S16b); the calendar cells, the week views and the DayPage list
> do **not**. The calendar orders by `createdAt` (insertion order, frozen at
> creation, so editing a start time never reorders anything) and `getEntriesByDate`
> — the DayPage list — has **no sort at all**, so its order is whatever Dexie's
> index walk returns. No new UI, no schema change: this is a correctness fix on
> read paths plus one shared comparator.

## Current state (verified 2026-08-15)

| Surface                                            | Reads through                                                                          | Orders by                                                       |
| -------------------------------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Month grid `DayCell`, `WeekView`, `WeekAgendaView` | `useEntriesInRange` → `getEntriesByDateRange`                                          | `date`, then **`createdAt`**                                    |
| DayPage list (`/day/:date`)                        | `useEntriesByDateQuery` → `getEntriesByDate`                                           | **nothing** (Dexie order)                                       |
| Optimistic calendar cache (no refetch)             | `patchRangeData` in `useEntries.ts` (create + update)                                  | `date`, then **`createdAt`**                                    |
| Reports `byEntry`                                  | `computeReport.ts:200`                                                                 | `date`, `startMinutes`, `id` ✅                                 |
| **Click-to-delete target** (active card)           | `dayClick.ts:48` — `bucket.find(e => e.date === date)` over the `entriesByCard` bucket | inherits the range query's order — **behavioral**, not cosmetic |

The first two reported symptoms fall out of rows 1–3: swapping 09:00 ↔ 11:00 leaves
`createdAt` untouched, so the chips keep their old order; a new entry gets the
newest `createdAt`, so it appends after every existing entry regardless of its
start time. Row 5 is the non-obvious consequence — see UR-32-5.

## Requirements

- **UR-32-1** — Editing an entry's start time reorders that day **everywhere** it is listed (month cell, week view, week agenda, DayPage), immediately, without a manual refresh.
- **UR-32-2** — A new entry added to a day that already has entries appears at its chronological position, not appended at the end.
- **UR-32-3** — Ordering is identical across all surfaces and stable across re-renders and refetches: entries sharing a start time never swap places on their own. A day with three or more entries re-sorts fully — every entry lands at its chronological position, not just the pair the user touched.
- **UR-32-4** — No behavior change to Reports ordering (it is already the target contract), to totals, to earnings, or to anything sync/Calendar-related.
- **UR-32-5** — Clicking a day cell with an active card that has **two or more entries on that date** deletes the day's **first (earliest-start)** entry, deterministically, and the confirm dialog names it. Today that click deletes the _oldest-created_ entry — a side effect of the range query's `createdAt` order, not a decision. This sprint makes it an explicit, tested choice.

## Notes

- **The DayPage bug is worse than the calendar one.** `getEntriesByDate` has no `sort` at all, so its order is a Dexie implementation detail — it can differ from the calendar's order for the same day _today_, before any edit. Task 2 is the single highest-value line in the sprint.
- **`dayClick` is the only place where entry-array order changes behavior rather than pixels.** Verified by grep: `dayClick.ts:48` is the sole `.find`/`[0]` over an entry bucket in non-test code; `earningsForEntry` / `monthlyEarningsPerEntry` consume `cardEntries` order-independently (count + sum only), so no money math moves. That is why UR-32-5 exists as its own requirement instead of riding along silently.
- **`getAllEntries` (Task 2) changes the snapshot's array order.** It feeds `lib/sync/snapshot.ts` and `calendar-sync/resyncAll.ts`. Consequences, all benign: `data.json` bytes change once → one extra push on the next sync; `bootstrap.ts` fingerprints re-sort by `id` (`:259`) so change-detection is unaffected; `lwwMerge` is id-keyed and order-independent; `resyncAll` only changes the order Calendar events are created in. **No snapshot `schemaVersion` bump** — the shape is identical.
- **Mixed-version devices are safe.** Ordering is a read-path concern only — no stored field changes — and the merge is id-keyed, so a device still on 1.3.2 and one on 1.3.3 converge to identical data; they merely render the same day differently until both update.
- **Rollback:** revert the commit. Every change is a read-path sort or a doc/test edit, so there is no data to undo — the only trace is one further `data.json` re-push (the `getAllEntries` order returning to its previous form), which is as harmless as the forward one. No env vars, no infra, no migration; a revert needs no coordination beyond a redeploy.
- **Do not sort inside components.** DayCell/WeekView/DayPage render whatever order the query hands them. Ordering lives in the query/patch layer so the optimistic cache and the refetched cache can never disagree — a component-level sort would mask a patch-layer bug instead of fixing it.
- **Google Calendar is the reference, and the user already sees it.** These entries sync to Calendar (S12), so the user compares the two surfaces side by side: in Calendar an event that changes time immediately moves to its place in the day, and same-start events show the longer one first. Tiers 1–3 of the comparator reproduce exactly that. `EntryChip` already prints `HH:MM` (`EntryChip.tsx:96`), so no UI work is needed for the times to read like Calendar's — only the order was wrong.
- **Tiers 4–5 are ours, not Calendar's.** Google breaks a start+duration tie by event title; our comparator takes `Entry` alone and has no card name (the DB layer returns entries without cards — adding a lookup would force `cardsById` through `getEntriesByDate`, `getAllEntries` and the snapshot builder for a cosmetic tie). `createdAt` stands in: for entries sharing a start time — the common case, since they inherit `card.defaultStartMinutes` — creation order is what a user expects, and `id` (a uuid, effectively random) stays only as the absolute last resort, preserving the S16b contract.
- **This is ordering, not a Calendar-style time grid — confirmed with the owner 2026-08-15.** The day surfaces stay lists of chips sorted by time. A real timeline (proportional vertical position, side-by-side lanes for overlapping entries, a now-line) was raised and explicitly declined: order is enough. Not a backlog item, not a deferral — out of scope by decision.
- **Explicitly NOT in S32:** no drag-to-reorder within a day (position is derived from start time, not stored — a manual order would need a new persisted field); no end-time/overlap display; no grouping by card; no change to `startMinutes` defaults or to the no-past-midnight-wrap rule (S16); no change to _whether_ a day-cell click deletes (only to which entry it targets — the delete-on-click flow itself is S05 behavior and stays).
- **Local-only workflow:** implement on the current branch, no new branch, no push, no PR — matches S29–S31.
