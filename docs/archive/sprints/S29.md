## Requirements (audit 2026-07-12)

- **UR-29-1** — An entry created or edited on device A while a sync flush / 412-merge / bootstrap pull is in flight must never be lost. (Audit Blocker #1)
- **UR-29-2** — Data pulled from Drive (bootstrap merge, 412 merge) must appear in the UI without a manual reload. (Audit Blocker #2)
- **UR-29-3** — A mutation made during an in-flight flush must reach Drive in the same session; the sync status must not report "synced" while queue rows remain. (Audit Warning #3)
- **UR-29-4** — Settings changes must sync like entries do and must not be silently reverted by a merge. (Audit Warnings #5–6)
- **UR-29-5** — A render-time crash must show a localized recovery screen, never a permanent white screen in the installed PWA. (Audit Warning #7)
- **UR-29-6** — A hung Google API request must not freeze sync for the rest of the session. (Audit Warning #9)
- **UR-29-7** — Security headers hardened: no `'unsafe-inline'` in `script-src`, HSTS present, `frame-ancestors` present. (Audit MED-1/MED-2/LOW-3)
- **UR-29-8** — The Playwright suite runs in CI; the `resyncAll` repair path has unit coverage; coverage tooling actually works. (Audit tests/CI #1–3)

## Acceptance Criteria

### Sync integrity (UR-29-1..3)

- [ ] Repro test: entry created between snapshot-build and merge-apply survives `applySnapshot` with its data intact — on both the 412 path and bootstrap
- [ ] `applySnapshot` performs no `clear()` on cards/entries; apply is one Dexie `rw` transaction with per-row LWW
- [ ] After a bootstrap/412 pull that changed data, the calendar shows the pulled entries without reload (query invalidation fired)
- [ ] A mutation enqueued during an in-flight flush drains in the same session; status is not `'synced'` while ready queue rows exist
- [ ] A hung Drive/Calendar request aborts at 30 s and enters the normal retry path; sync status never sticks at `'syncing'` forever

### Settings (UR-29-4)

- [ ] Changing a setting enqueues a push without needing an entry/card edit
- [ ] A settings change on device A survives a merge against a snapshot with newer `exportedAt` but older prefs (`settingsUpdatedAt` wins)
- [ ] Concurrent settings writes (sync bookkeeping vs UI toggle) lose nothing

### Resilience & security (UR-29-5, UR-29-7)

- [ ] A thrown render error shows the localized recovery screen with a working Reload; corrupted persisted `anchorDate` falls back to today
- [ ] Deployed CSP has no `'unsafe-inline'` in `script-src`; HSTS and `frame-ancestors 'none'` present; post-deploy smoke test (sign-in, backup, calendar sync, install) shows zero CSP violations
- [ ] Day-click create failure shows an error toast

### Tests & CI (UR-29-8)

- [ ] Playwright (both projects) runs on every push/PR to main; report uploaded on failure
- [ ] `resyncAll` covered: mode filter, create-vs-patch, error accumulation, throttle
- [ ] Coverage runs in CI with thresholds on `features/sync`, `features/backup`, `lib`
- [ ] `format:check` in CI; axe gate includes `serious`
- [ ] Reports shows the monthly-retainer sub-line; `KNOWN_PLACEHOLDERS` in i18n-check is empty

### Cleanup

- [ ] `pkce.ts`, `refreshAccessToken`, `monthlyEarningsForPeriod` gone; grep for their names returns only journal/spec mentions
- [ ] `sprints/S27.md` and `sprints/S28.md` committed; IMPLEMENTATION_PLAN tracker current through S29
- [ ] Drag pick-up no longer re-renders every calendar cell (React Profiler, once, recorded in PERF_NOTES.md)

## Notes

- **Part A is the sprint.** Everything else can slip to a followup; the 412-merge data-loss window (Task 1) and invisible pulls (Task 3) cannot — they corrupt/hide user data in the product's core two-device scenario. If time-boxing, land Parts A+B, then D (three tiny edits), then E, then C, then F.
- **Task 1 changes destructive-write semantics — test first.** Write the Task 2 repro tests against current code (they must FAIL, demonstrating the loss), then implement. This is the one place in the sprint where TDD is non-negotiable.
- **No Dexie/snapshot version bumps in this sprint.** `settingsUpdatedAt` (Task 6) is an additive optional field readable by old snapshots. Dexie stays v6, snapshot stays v3 — S27/S28 own the next bumps; do not create a version-number collision with their specs.
- **Task 15 (CSP) risk is deploy-time, not code-time.** The change is two characters of config, but a missed inline script breaks the whole app at the CDN. Deploy to a Vercel preview first and run the smoke checklist there before promoting.
- **Scope discipline — explicitly NOT in S29:** the bundle-shrink to ≤500 KB (own sprint, S30 candidate: lazy auth-gated `lib/google/*` + SyncManager — also the natural moment to revisit `chunkSizeWarningLimit`); S27 Payments; S28 Reminders; per-field settings timestamps beyond the single `settingsUpdatedAt` (single stamp is enough for a single user); BroadcastChannel cross-tab auth propagation, SW "reload to update" affordance, manifest localization, DayCell/announcement a11y polish (audit Suggestions #10–13 + D3/D4 — file as backlog, cheap but not urgent); Web Push / anything requiring a backend.
