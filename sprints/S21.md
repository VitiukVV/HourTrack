# S21 -- Calendar Polish + Monthly Rate Feature (Schema v3)

**Repo**: main | **Type**: FE | **Phase**: V2
**Size**: L-XL | **Dependencies**: S19 (palette + bg-color treatment), S20 (Reports filter + table contract)
**Plan Sources**: chat 16/05/2026 (UR-21-1..UR-21-5), plan file `abstract-cuddling-star.md`

> **Goal:** make the calendar Month / Week views feel uncluttered (project
> name instead of times in MonthView chips, no more colored dots, no more
> per-day total-hours/EUR footer), add visual separators between days in
> WeekView, and ship a new rate type for retainer-style projects:
> `rateType: 'monthly'`. Monthly cards charge a flat amount per month
> regardless of hours logged; entries on such cards show "—" in the
> Reports Sum column, and the Reports totals card adds the monthly
> retainer for every month that contains at least one entry of that card.

## User requirements (chat 16/05/2026)

- **UR-21-1** — In the Month calendar view, show the project name instead of the time on each chip; truncate as needed; drop the color dot (the chip background already carries the color).
- **UR-21-2** — Remove the per-day total markers in the Month calendar view: total hours and total earnings.
- **UR-21-3** — Add vertical borders in the Week calendar view so individual days are visually distinct.
- **UR-21-4** — Add a "monthly total" rate type: e.g. Mary, 250 EUR / month regardless of how many days were worked.
- **UR-21-5** — In Reports: for monthly-rate cards, the table's Sum column shows "—" (per row); the grand Total adds the full monthly amount.

## Notes

- **Monthly rate is a retainer model, not a fixed-budget split.** Fixed-rate (`'fixed'`) cards split `fixedTotal` proportionally across entries. Monthly cards charge a flat amount per calendar month that has at least one entry — they don't care about hours. Two distinct models; keep the `Card` rateType discriminator clear.
- **Decision (locked per user 2026-05-16):** monthly billing per "month with ≥1 entry", NO PRORATION. A user with NO entries in May for Mary owes 0 EUR for May. A custom date range that spans half-April + half-May with entries in both months bills full 250 + 250 = 500 EUR — not a 1.5-month proration (≈375). This matches the "tracking what I worked on, regardless of working days" semantics from the user's original example.
- **Custom payment still wins.** If a monthly-card entry has `useCustomPayment=true`, that custom amount is used (and counted toward Reports total). The `monthlyTotal` doesn't apply on top — those entries are treated as one-off line items. Document this in the `earningsForEntry` comment block.
- **Dexie v3 upgrade is a no-op for existing rows.** The `monthlyTotal` column appears with value `null` everywhere. No rateType changes; no data loss. Crucially: existing cards remain in their current `'hourly'` / `'fixed'` mode. Users opt into monthly explicitly by editing a card.
- **Drive snapshot v3** is the breaking schema bump. v2 snapshots from existing users restore fine (backfill `monthlyTotal: null`); new exports are v3. Make sure restore.ts has explicit `if (snapshot.schemaVersion === 2) { ... }` migration branch — don't rely on "current shape == future shape".
- **DayCell footer removal is a real subtraction**, not a hide. The reducer that totalled duration + earnings is gone. If a future sprint reinstates a "click day for quick stats", it's a new feature, not a revert.
- **MonthView chips become name-only**, which means the user can't see start times at a glance — only on hover / tap. That's a deliberate density trade. The Week and Day views still show times prominently.
- **WeekView borders are visual-only.** Don't refactor grid spacing or column widths to accommodate the new borders — just `border-r last:border-r-0` on each column wrapper.
- **Archived monthly card semantics:** if `showArchived=true` and an archived monthly card has entries in the period, it counts toward the total like any active card (existing pool semantics). If `showArchived=false`, the card is excluded from `selectedCardIds` before aggregation, so its retainer doesn't appear — same behaviour as hourly/fixed cards today. No new logic needed; this is documented for the integration test.
- **What this sprint does NOT do:**
  - Mixed-rate billing (e.g. monthly retainer + hourly overflow) — out of scope, ask user if they need it.
  - Prorated month billing (start mid-month → charge half) — locked OUT by user decision (full month per billable month).
  - Year/quarter retainer — out of scope.
  - Currency localisation — still EUR-only across the app.
