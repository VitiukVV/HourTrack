## Requirements (audit 2026-07-17)

- **UR-31-1** — A card the user has fully paid (paying the exact amount the UI displayed) must read as `paid`, not `partial`/`overdue`. Cent-level float residue must never mark money as owed. (Audit Blocker #1)
- **UR-31-2** — Permanently deleting a card must not leave its payment rows behind; orphaned payments must not silently vanish from ledgers, become undeletable, or re-sync forever. (Audit Warning #2)
- **UR-31-3** — A Calendar create op that is retried after a crash/tab-close must not create a duplicate event; a create for an entity that already has a `googleEventId` must patch, not insert. (Audit Warning #3)
- **UR-31-4** — A concurrent read-modify-write on the same entity (sync stamp vs user edit, cross-tab) must not lose `googleEventId` or user edits. (Audit Warning #4)
- **UR-31-5** — A preference change on device B (e.g. theme) must not null device A's cached `hourtrackCalendarId` and trigger a duplicate "HourTrack" calendar. (Audit Warning #6)
- **UR-31-6** — A truncated/corrupt/null-array `data.json` pulled from Drive must surface as a recoverable error, never a hard `TypeError` that wedges sync (push retries forever / bootstrap fails every boot). (Audit Warning #5)
- **UR-31-7** — The audit's highest-value missing tests exist: 412-conflict merge orchestration, backup RESTORE roundtrip, token-refresh worker loop, offline queue-drain, RemindersScheduler fire-once/cleanup. (Test audit P0–P1)
- **UR-31-8** — Security posture documented/hardened: Drive-plaintext-at-rest decision recorded, the false "IndexedDB = XSS containment" comment corrected, COOP header added. (Security M1/L2/L4)
- **UR-31-9** — README reflects reality: snapshot `schemaVersion 5` with payments/reminders, current tool versions, current sprint range. (Deps/arch #1)

| 1   | Epsilon-tolerant payment status                       | Logic | `apps/web/src/features/payments/paymentStatus.ts:25-29`                                | `expected` flows from `earningsForEntry = (durationMin/60)*hourlyRate` (unrounded), but the Mark-paid dialog pre-fills `Number(remaining.toFixed(2))` — so paying the displayed amount leaves a sub-cent residue. This + Task 1 are belt-and-suspenders — the epsilon fixes status, the rounding fixes the displayed totals.                                                           |
| 3   | Payment-correctness tests                             | Test  | `paymentStatus.test.ts`, `monthLedger.test.ts` (colocated)                             | **Write first, watch them fail against current code**, then implement Tasks 1–2. ### Part B — Data integrity (Warnings; UR-31-2..6)

| 4   | Cascade payments on card hard-delete         | DB    | `apps/web/src/lib/db/queries.ts:232-252` (`deleteCardPermanently`)                                                                                         | The `rw` transaction touches only `cards`/`entries`/`tombstones`; `Payment.cardId` rows survive → invisible in ledgers (`cardsById.get` undefined at `monthLedger.ts:103`), undeletable, and re-sync forever. | 6   | Atomic `update*` (single `rw` txn)           | DB    | `apps/web/src/lib/db/queries.ts` — `updateEntry:340`, `updatePayment:449`, `updateCard:176`, `updateReminder:575`                                          | Each is get→spread→put across **three** IndexedDB transactions; a concurrent stamp vs user edit (cross-tab / edit-during-flush) lets the second `put` clobber the first — losing `googleEventId` (→ orphan event) or the user's edit. | 7   | Preserve `hourtrackCalendarId` across merges | Sync  | `apps/web/src/features/sync/lwwMerge.ts:88-109` (`mergeSettings`)                                                                                          | `mergeSettings` copies the whole preference block (incl. `hourtrackCalendarId`) from the side with the newer `settingsUpdatedAt`, but calendar-id writes don't bump `settingsUpdatedAt` (excluded from `PREFERENCE_KEYS`). Move `hourtrackCalendarId` out of the `winningPrefs` block into the **device-local keep-ours** block (`:106-109`, alongside `driveDataFileId`/`driveDataEtag`) — the calendar-name lookup in `ensureCalendar` re-resolves the same id on a device that has none.
