# S30 -- "What's New" Page (Settings)

**Repo**: main | **Type**: FE | **Phase**: V3 Feature
**Size**: S | **Dependencies**: none (touches S08 Settings page, S23 lazy-route pattern)
**Plan Sources**: user authorized in-session 2026-07-17 as a follow-on sprint to run after S27/S28/S29 -- a changelog surface hosted at the bottom of Settings, in the style of common in-app "what's new" pages (what was added and how it works).

> **Goal:** give the user a changelog surface inside the app -- a "What's
> New" entry at the bottom of Settings (after About) that opens a page
> listing recent releases, what changed, and a one-line explanation of how
> each change works. Follows the common in-app-changelog pattern (Slack,
> Linear, Notion, etc.): a static, hand-written release list rendered
> newest-first, plus a small "unseen update" indicator on the entry point.

## Why a static, hand-authored list (not generated from git log)

`git log` is full of internal/refactor noise (dependency bumps, chore
commits, spec-only commits that never shipped code). A user-facing changelog
must describe what actually shipped, in plain language, so content is a
maintained data file (`changelog.ts`) that a human (or the sprint that ships
a feature) updates -- exactly like S27/S28/S29 are entries in
`docs/IMPLEMENTATION_PLAN.md` today, just user-facing instead of internal.

## Why "seen" state is localStorage-only, not a synced Settings field

The S24/S29 precedent establishes that **any new persisted field on
`Settings` requires a Dexie version bump + Drive snapshot `schemaVersion`
bump + `validateSnapshot` + LWW merge wiring** (see `onboardingSeen` in
`OnboardingProvider.tsx` for the full cost of a synced boolean). Whether the
user has dismissed the "new update" badge is a pure UI nicety with zero
data-integrity value -- worst case on a new/second device is the badge shows
once more. Storing it in `localStorage` (mirrors `LANGUAGE_STORAGE_KEY` in
`lib/i18n.ts`) gets the desired UX for zero schema risk. **No Dexie bump, no
snapshot bump in this sprint.**

## User requirements

- **UR-30-1** -- A "What's New" entry sits at the bottom of the Settings page, after the About section, and navigates to a dedicated page.
- **UR-30-2** -- The page lists releases newest-first, each with a version/date and a short list of what changed and how it works (plain-language bullets, not commit messages).
- **UR-30-3** -- The entry point shows a lightweight "new" indicator when there is a release the user hasn't opened the page since; opening the page clears it.
- **UR-30-4** -- Content is trilingual (uk/en/es), consistent with the rest of the app; no hard-coded language strings in components.
- **UR-30-5** -- Adding this page bumps the app to v1.1.0 and the page's own top entry documents this exact feature (dogfooding: the changelog announces itself).

## Notes

- **Scope discipline:** no modal/toast "what's new since last visit" popup on app open -- a Settings-hosted page, not an interruptive surface. A future sprint could add a soft in-app nudge if wanted; not built here.
- **No backend, no push notifications** -- consistent with the project: 100% client-side, static content shipped in the bundle.
- **Content maintenance convention going forward:** any sprint that ships a user-visible feature should add one entry to `CHANGELOG_RELEASES` + its i18n keys as part of that sprint's own scope.
- **Local-only workflow:** implemented directly on the current branch (`sprints/27-28-29-payments-reminders-audit`), no new branch, no push, no PR.
