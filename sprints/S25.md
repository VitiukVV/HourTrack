# S25 -- Drag-and-Drop Entry Reschedule (move entry to another day)

**Repo**: main | **Type**: FE | **Phase**: Post-V2 Feature
**Size**: L | **Dependencies**: S16 (`startMinutes`/`durationMin` data shape), S17 (EntryEditModal + chip-click edit), S18 (responsive WeekView grid + mobile WeekAgendaView), S23 (surgical range-cache patches + `memo(DayCell/EntryChip)`)
**Plan Sources**: user request 2026-06-24 — "Можливість перенести (перетягнути) існуючий запис на інший день тижня."

> **Goal:** let the user move an existing entry to a different day by dragging
> its chip — on the Month grid, the Week grid, AND the mobile Week agenda —
> with first-class touch support (this is a mobile-first PWA). Reschedule
> changes ONLY the entry's `date`; time-of-day (`startMinutes`), duration,
> payment and note are preserved. As a keyboard-/precision-accessible
> complement, also add an explicit **date field** to the entry edit modal so
> the same move is possible without dragging. The data layer is already
> reschedule-ready (`useUpdateEntryMutation({ id, patch: { date } })` +
> `patchRangeData` already removes-from-old-bucket / inserts-at-new), so this
> sprint is a UI-only addition.

## User requirements (user request 2026-06-24)

- **UR-25-1** — A user must be able to drag an existing entry chip from one day and drop it on another day to reschedule it. Only the calendar day changes; everything else about the entry stays the same.
- **UR-25-2** — This must work well on touch devices (mobile-first), not just with a mouse. A quick tap must still open the entry editor; only a deliberate press-and-hold should start a drag, and the page/column must still scroll normally.
- **UR-25-3** — Reschedule must be available on both the Month view and the Week view (and the mobile Week agenda, which is the `< md` rendering of the Week view).
- **UR-25-4** — A user must also be able to change an entry's date from inside the entry editor modal (keyboard-accessible, precise, and works when the target day isn't on screen to drop onto).

## Acceptance Criteria

### Reschedule by drag (UR-25-1, UR-25-3)

- [ ] Dragging an entry chip onto a different day moves the entry to that day; the chip disappears from the source day and appears on the target day without a full refetch (surgical S23 patch path)
- [ ] Only `date` changes — `startMinutes`, `durationMin`, payment fields and `note` are byte-identical after the move
- [ ] The move is persisted (survives reload) and a Google Calendar PATCH is enqueued (via the existing `enqueueUpdateCalendarEvent`)
- [ ] Dropping a chip back on its own day is a no-op — no mutation, no Calendar PATCH, no toast
- [ ] Works in MonthView, the `≥ md` WeekView grid, AND the `< md` mobile WeekAgendaView (including dropping on an empty day)

### Mobile / touch (UR-25-2)

- [ ] On touch, a deliberate press-and-hold (~220 ms) starts the drag; a quick tap still opens the entry edit modal
- [ ] Vertical scrolling of the page / week columns / agenda still works normally when not press-holding a chip
- [ ] A `<DragOverlay>` clone follows the finger/pointer; the drop target is visibly highlighted while hovered
- [ ] Auto-scroll lets the user drag to an off-screen day in scrollable containers

### Change date in the editor (UR-25-4)

- [ ] The entry edit modal shows a date field initialised to the entry's current date
- [ ] Changing it and saving moves the entry to the new date (same mutation path as drag); the calendar surface reflects it
- [ ] Leaving the date unchanged round-trips the entry untouched (no spurious dirty/save)

### Accessibility & quality

- [ ] Entries are reschedulable via keyboard (KeyboardSensor: pick up, move, drop)
- [ ] Localized screen-reader announcements fire on pick-up / over / drop / cancel (uk/en/es)
- [ ] A success toast with a working Undo appears after a drag move (Undo restores the original date); a failed move shows an error toast and leaves the chip in place
- [ ] Stage 0 spikes (S0a React 19 compat, S0b touch scroll-vs-drag, S0c bundle) are resolved and their decisions recorded before Part B/C UI work
- [ ] A drag does not re-render all calendar cells (verified once under React Profiler)
- [ ] Axe-core e2e stays green on the calendar surfaces
- [ ] `pnpm -F web typecheck`, `lint`, `test`, and `e2e` (incl. the new desktop + mobile drag specs) are all green
- [ ] Index bundle stays within the S23 budget (or the budget is raised in this PR with a recorded rationale)

## Notes

- **Data layer is already done.** `useUpdateEntryMutation({ id, patch: { date } })` + `patchRangeData` (`useEntries.ts:219-235`) already implement the move (remove-from-old-bucket / insert-at-new), and the Calendar PATCH is wired. This sprint adds NO mutation/DB/sync code — it is purely the DnD UI plus the editor date field. If you find yourself editing `queries.ts` or `SyncManager`, stop — you've gone out of scope.
- **Why `@dnd-kit` and not native HTML5 DnD.** This is a mobile-first PWA. Native HTML5 drag-and-drop is broken on touch and has no keyboard story. `@dnd-kit` gives PointerSensor (with press-hold activation), KeyboardSensor, DragOverlay, auto-scroll, and accessibility announcements out of the box. The agreed trade is one ~10 KB dependency.
- **Do Stage 0 first.** S0a (React 19 compat), S0b (touch scroll vs drag), and S0c (bundle) are the three assumptions this plan rests on. They're cheap to validate and expensive to discover mid-implementation. If S0a fails, the whole library choice is back on the table.
- **The press-hold delay is load-bearing — and so is using `TouchSensor` for touch.** `activationConstraint: { delay: 220, tolerance: 8 }` on a `TouchSensor` is what lets a swipe scroll while a hold starts a drag. A single PointerSensor for all inputs forces the scroll-vs-drag trade onto `touch-action: none`, which kills list scroll on the agenda — exactly UR-25-2's failure mode. Branch sensors by input type; do not drop the delay to make desktop "snappier" (use a `distance` constraint on the mouse PointerSensor instead).
- **Don't break the S23 memo/patch optimisations.** `memo(DayCell)` and `memo(EntryChip)` rely on prop reference stability and surgical cache patches. `useDroppable`'s `isOver` only flips for the hovered cell, so only that cell re-renders — fine. Pass `dragEnabled` as a primitive prop (stable). Do not start allocating fresh `entries` buckets in the parent to pass drag data.
- **Same-day no-op is mandatory.** A drop that lands on the origin day must short-circuit in `resolveEntryMove` BEFORE any mutation — otherwise every accidental pick-up-and-drop fires a needless Calendar PATCH and a sync round-trip.
- **Cross-month / off-range drops.** In MonthView the leading/trailing days belong to adjacent months; dropping there is a valid move. `patchRangeData` will remove the entry from the currently-cached range if the new date falls outside it — that's correct (the chip leaves the visible grid). No special handling needed beyond using the dropped cell's `date` id.
- **Editor date field is the accessible twin of drag**, not a redundant feature: it covers keyboard users, precise edits, and moving an entry to a day that isn't currently on screen to drop onto. It reuses the exact same mutation, so the marginal cost is small.
- **Testing DnD — set expectations.** happy-dom returns zero geometry, so dnd-kit collision detection (and thus KeyboardSensor moves) may NOT resolve a droppable in jsdom. Treat the **pure resolver + `onDragEnd` callback unit tests (Task 20) as the source of truth** for logic, and **Playwright (Tasks 22/23) as the source of truth for real drag** — desktop needs a step-wise `mouse.down/move×N/up` helper, touch needs a delayed touch-event sequence. The KeyboardSensor jsdom test (Task 21) is best-effort; don't gate the sprint on it. Budget real time for the mobile touch e2e — it's the hardest piece.
- **No optimistic move.** The chip moves only after the mutation's `onSuccess` patch lands (Dexie write is fast). On failure nothing moved, so the error path is just a toast — no rollback. Don't "improve" this into an optimistic move with manual rollback without a reason; it adds a reconciliation bug surface for negligible perceived-latency gain.
- **What this sprint does NOT do:**
  - Multi-entry / range drag-select. (Single entry only.)
  - Drag to reorder entries within the same day, or drag to change time-of-day. (Out of scope — date only.)
  - Drag across calendar views (e.g. from a mini-month into the week). (No.)
  - Reassign an entry to a different card via drag. (Still a future "reassign entry" flow, per the EntryEditor S06 note.)
